## Context

`openspec validate --all --strict` は、確定した仕様 `expense-claims` の要件のうち、3 番目（「申請の一覧」）と 11 番目（「月ごとの集計」）の本文が 500 文字を超えているという WARNING を出し、strict で失敗する。どちらの要件も、出し直し（allow-resubmit-rejected-claim）と取り下げ（allow-withdraw-pending-claim）を足すたびに、例外の扱いを本文に書き足してきた。

この変更でコードは変えない。`src/` の振る舞いは既存のテストで確かめられているため、変えるのは仕様の書き方と、仕様に合わせて名前を付けたテストのグループだけである。

検証では、次の 2 つの制約がわかった。

- MODIFIED は要件のブロック全体を置き換えるため、確定した仕様にあるシナリオを MODIFIED から外すと、検証とアーカイブが拒否する（「omits scenario(s) the current spec still has」）。
- 同じ名前の要件を REMOVED と ADDED の両方に書くことはできない（「Requirement present in both ADDED and REMOVED」）。

## Goals / Non-Goals

**Goals:**

- アーカイブした後の `openspec validate --all --strict` を成功させる。
- 分けた後の各要件が、1 つのまとまった振る舞いだけを述べるようにする。
- シナリオは文言を変えずにすべて残し、どれかの要件に属させる。
- テストの `describe` の名前を要件名と一致させる。

**Non-Goals:**

- API・データベース・`src/` の変更。
- シナリオやテストの確認内容の追加・削除・変更。
- 500 文字を超えていない他の要件の整理。

## Decisions

### 1. 元の要件を REMOVED にし、新しい名前の 2 つの要件を ADDED で足す

「申請の一覧」と「月ごとの集計」をそれぞれ削除し、次の 4 つを追加する。

| 元の要件 | 分けた先 | 本文に残す内容 | 移すシナリオ |
|---|---|---|---|
| 申請の一覧 | 申請の一覧の対象と並び順 | 200 を返す、新しい順、申請者は自分の申請だけ、承認者はすべて | 申請者は自分の申請だけを見る／承認者はすべての申請を見る／申請がない |
| 申請の一覧 | 一覧の申請の項目 | 13 個の項目と、`null` になる条件 | 差戻し理由が一覧に含まれる／差戻されていない申請の理由は null／出し直しの紐付けが一覧に含まれる／取り下げていない申請の取り下げ日時は null |
| 月ごとの集計 | 月ごとの集計の対象と応答 | 承認者が呼ぶ、`date` で月を判定、全申請者が対象、`month` と `byStatus` の形、`0` の扱い | 状態ごとに集計される／経費の日付で月を判定する／すべての申請者の申請が対象になる／該当する申請がない |
| 月ごとの集計 | 集計での取り下げと出し直しの扱い | 取り下げは `withdrawn` だけに数える、出し直しと元の申請を別々に数える、`byStatus.rejected` の意味 | 差戻した申請と出し直した申請は別々に数えられる／取り下げた申請は未判断に数えない |

本文と規則の文は、元の本文の文をそのまま分けて使う。言い換えたのは次の 2 か所だけである。

- 「取り下げた申請は `pending` には数えない」を、規範の文として「`byStatus.pending` に数えてはならない（MUST NOT）」と書いた。
- それぞれの分けた先から、もう一方を参照する 1 文（「…は『一覧の申請の項目』に従う」など）を足した。

代わりに考えた方法：

- **MODIFIED で本文とシナリオを減らし、残りを ADDED で足す**：要件名は変わらないが、上のとおり検証で拒否される。
- **REMOVED と ADDED に同じ名前を書く**：同じく拒否される。
- **RENAMED と MODIFIED を組み合わせる**：名前を変えても、MODIFIED でシナリオを外す点は変わらないため、同じ検証にかかる。
- **シナリオを減らさず、MODIFIED で本文だけを短くする**：項目や `null` の規則を本文から外すと、その規則を述べる要件がなくなる。シナリオだけに規則が残り、要件と一致しなくなる。

### 2. 「一覧の状態による絞り込み」は MODIFIED で参照先だけを直す

この要件の本文は「『申請の一覧』で返す対象」と「並び順と各申請の項目は『申請の一覧』と同じ」と参照している。参照先を「申請の一覧の対象と並び順」と「一覧の申請の項目」に直す。シナリオ 7 件はそのまま写す。振る舞いは変わらない。

### 3. テストは describe の名前と置き場所だけを直す

`test/expense-claims.api.test.js` の `describe` は要件名でまとめてある。

- `describe('申請の一覧')`：名前を「申請の一覧の対象と並び順」に変える。項目を確かめる 4 つのテストは、新しい `describe('一覧の申請の項目')` に移す。`listClaims` などの補助関数はファイルの先頭にあるため、移しても動く。
- `describe('月ごとの集計')`：集計の権限と月の検証のテストも入っており、補助関数 `getSummary`・`createOn`・`zero` はこの中にある。外側の `describe` の名前は変えず、その中に `describe('月ごとの集計の対象と応答')` と `describe('集計での取り下げと出し直しの扱い')` を入れ子で作り、該当するテストを移す。補助関数を外に出す必要はない。
- テストの中身（呼び出しと `assert`）は変えない。「承認者はすべての申請を見る」のテストは、項目の一覧（キーの並び）と `null` も確かめている。このテストは「申請の一覧の対象と並び順」に残す。項目の規則は「一覧の申請の項目」の 4 つのテストでも確かめられる。

### 4. 確定した仕様には、アーカイブで反映する

`openspec/specs/expense-claims/spec.md` を手で書き換えず、`openspec archive` で差分を当てる。アーカイブでは、追加した 4 つの要件が仕様の末尾に並ぶ。

## Risks / Trade-offs

- [要件名が変わる] 「申請の一覧」「月ごとの集計」という名前で仕様を参照しているものが古くなる。→ アーカイブ済みの変更と ADR-0007 の Source 欄は、当時の記録なので書き換えない（ADR は変更しない決まり）。今の仕様の中にある参照は決定 2 で直し、テストの `describe` は決定 3 で直す。`src/` のコメントなどに古い要件名が残っていないかは、実装のタスクで確かめる。
- [追加した要件が仕様の末尾に並ぶ] 一覧と集計の要件が仕様の中で離れ、読みにくくなる。→ 分けた先の要件どうしは本文で互いの名前を参照しており、たどることはできる。並び順を直すには確定した仕様を手で編集する必要があり、アーカイブの手順から外れるため、この変更ではやらない。
- [移すときにシナリオが抜ける・変わる] → 移したシナリオの数（一覧 7 件 → 3 件 + 4 件、集計 6 件 → 4 件 + 2 件）と文言を、確定した仕様と照らし合わせる。テストの数と名前が変わらないことも `npm test` の結果で確かめる。
- [同じ問題がまた起きる] 機能を足すたびに例外の扱いを既存の要件に書き足すと、また 500 文字を超える。→ この変更では仕組みを足さない。次からは、例外の扱いを足すときに別の要件にするかどうかを提案の段階で考える。

## Migration Plan

デプロイは不要（コードを変えない）。アーカイブした後で `openspec validate --all --strict` を実行し、成功を確かめる。戻す場合は、アーカイブのコミットを戻す。
